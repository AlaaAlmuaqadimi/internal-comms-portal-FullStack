# اختبار يدوي لواجهة المكالمات — المرحلة A

هذا الدليل يشرح تجربة واجهة `/api/calls` و`/api/settings/app` بدون كتابة أي طلب يدوياً،
باستخدام مجموعة Postman الجاهزة في هذا المجلد.

> كل ما هنا للتطوير فقط. الحسابات التجريبية ينشئها سكربت منفصل ولا علاقة لها ببيانات
> الإنتاج. لم يتم تغيير أي قاعدة عمل في هذه المرحلة.

## 1. المتطلبات

1. قاعدة بيانات MySQL/MariaDB مطبَّق عليها الترحيلات:

   ```bash
   npm run migrate --prefix backend
   ```

2. الخادم يعمل:

   ```bash
   npm run dev --prefix backend
   ```

   وتأكد من `GET http://localhost:4000/health` أنه يعيد `{"success":true,"status":"ok"}`.

3. ملفات المجموعة:
   - `backend/docs/calls.postman_collection.json`
   - `backend/docs/calls.postman_environment.json`

## 2. الحسابات التجريبية

أنشئها (أو أعد ضبطها) بأمر واحد:

```bash
npm run seed:calls --prefix backend
```

| الحساب | اسم المستخدم | الوحدة | الدور | ملاحظة |
| --- | --- | --- | --- | --- |
| المدير | `dev.director` | `root` | employee | قيادي بحكم نوع الوحدة |
| الوكيل | `dev.deputy` | `deputy` | employee | قيادي بحكم نوع الوحدة |
| موظف 1 | `dev.employee1` | `u53` (قسم) | employee | موظف عادي |
| موظف 2 | `dev.employee2` | `u24` (إدارة) | employee | موظف عادي، وحدة مختلفة |
| مسؤول النظام | `dev.admin` | `u1` (مكتب) | admin | لتعديل الإعدادات فقط |

### من أين تأتي كلمات المرور؟

لا توجد أي كلمة مرور داخل المستودع. عند تشغيل `seed:calls`:

- إن لم تحدد كلمة مرور، يولّد السكربت كلمة عشوائية ويعرضها **مرة واحدة** في الطرفية.
- أو اختر كلمة مرور بنفسك عبر متغيّر البيئة:

  ```powershell
  # PowerShell (Windows)
  $env:DEV_SEED_PASSWORD="MyDevPass123"; npm run seed:calls --prefix backend
  ```

  ```bash
  # bash
  DEV_SEED_PASSWORD=MyDevPass123 npm run seed:calls --prefix backend
  ```

- أو شغّل السكربت مباشرة:

  ```bash
  node backend/scripts/seed-call-demo-users.js --dev-password MyDevPass123
  ```

> لا تستخدم `npm run ... -- --dev-password ...`؛ بعض إصدارات npm تبتلع هذه الأعلام
> فلا تصل إلى السكربت. متغيّر البيئة هو الطريق الموثوق.
> ولا تستخدم `--password` أبداً، لأن npm يلتقطه كإعداد خاص به.

انسخ كلمة المرور المعروضة إلى متغيّرات البيئة في Postman:
`employee1Password`, `employee2Password`, `directorPassword`, `deputyPassword`, `adminPassword`.

## 3. الاستيراد في Postman

1. Postman → Import → اختر الملفين (المجموعة والبيئة).
2. اختر البيئة `ICP Calls — Phase A (local)` من أعلى اليمين.
3. عدّل `baseUrl` إذا لم يكن الخادم على `http://localhost:4000`.
4. املأ متغيّرات كلمات المرور الخمسة من مخرجات السكربت.

> Thunder Client يستورد ملف Postman أيضاً، لكن سكربتات الاختبار التلقائية قد لا تعمل؛
> الاستجابة نفسها صحيحة، أما التأكيدات فتعمل بشكل كامل في Postman أو Collection Runner.

## 4. خطوات الاختبار والنتيجة المتوقعة

شغّل المجلدات بالترتيب (أو استخدم Collection Runner). كل طلب يحتوي تأكيدات تلقائية
تظهر باللون الأخضر عند النجاح.

### المجلد 0 — تسجيل الدخول والبحث

| الخطوة | المتوقع |
| --- | --- |
| تسجيل دخول الحسابات الخمسة | `200` مع `accessToken` محفوظ في البيئة |
| البحث في الدليل `q=dev.` | `200`، ويُحفظ `employeeId` لكل حساب |
| قراءة الإعدادات الحالية | `200`، وتُحفظ قيمة `call.redacted_label.director` الحالية |

### المجلد 1 — المصفوفة الممنوعة

| الخطوة | المتوقع |
| --- | --- |
| موظف 1 → المدير | `403` مع `code = CALL_TARGET_FORBIDDEN` |
| موظف 1 → الوكيل | `403` وبنفس الرسالة |
| موظف 1 → معرّف غير موجود | `403` وبنفس الرسالة تماماً (لا فرق بين موجود وغير موجود) |
| موظف 1 → نفسه | `403` |

كل محاولة مرفوضة تُكتب في `audit_log` بفعل `call.denied`، والسبب الداخلي في `metadata`
مثل `TARGET_LEADERSHIP` أو `TARGET_NOT_FOUND` أو `SELF_CALL`.

### المجلد 2 — المسموح للقيادة

| الخطوة | المتوقع |
| --- | --- |
| المدير → الوكيل | `201`، والحالة `ringing` |
| الوكيل → المدير | `201` |

### المجلد 3 — مكالمة عادية بين موظفين

| الخطوة | المتوقع |
| --- | --- |
| موظف 1 → موظف 2 (وحدتان مختلفتان) | `201` |
| موظف 2 يقرأ المكالمة | `direction = incoming`, `redacted = false`, `canCallBack = true`, `iceTransportPolicy = all` |
| موظف 2 يقبل | `accepted` |
| موظف 2 ينهي | `ended` |

### المجلد 4 — الرفض بدون إشعار

| الخطوة | المتوقع |
| --- | --- |
| موظف 1 → موظف 2 ثم موظف 2 يرفض | `rejected` |
| عدّاد غير المقروء لدى موظف 2 | لم يتغيّر (الرفض لا يُنشئ إشعاراً) |

### المجلد 5 — الإلغاء

| الخطوة | المتوقع |
| --- | --- |
| موظف 1 → موظف 2 ثم موظف 1 يلغي | `cancelled` |

### المجلد 6 — سجل المكالمات

| الخطوة | المتوقع |
| --- | --- |
| `GET /api/calls` لموظف 1 | `200` مع مصفوفة `calls` غير فارغة |

### المجلد 7 — إخفاء هوية القيادة والإشعار

| الخطوة | المتوقع |
| --- | --- |
| المدير → موظف 1 | `201`، `relayOnly = true` |
| موظف 1 يقرأ المكالمة | `redacted = true`, `caller.employeeId = null`, `caller.name = المدير العام`, `canCallBack = false`, `iceTransportPolicy = relay` |
| سجل موظف 1 | نفس المدخل بنفس الاسم المخفي و`canCallBack = false` |
| موظف 1 يسجّل المكالمة كفائتة | `missed` |
| إشعارات موظف 1 | إشعار نصّه `مكالمة فائتة من المدير العام` ولا يظهر الاسم الحقيقي للمدير |

> إن كنت قد غيّرت التسمية مسبقاً، فالسكربت يقرأ القيمة الحالية من الإعدادات ويستخدمها،
> لذلك تنجح التأكيدات دائماً بالقيمة الفعلية.

### المجلد 8 — الإعدادات

| الخطوة | المتوقع |
| --- | --- |
| `GET /api/settings/app` كموظف عادي | `200` |
| `PATCH /api/settings/app` كموظف عادي | `403` |
| `PATCH` كمسؤول النظام بتغيير تسمية المدير | `200` مع القيمة الجديدة |
| `GET` بعد التعديل | يعيد القيمة الجديدة فوراً (لا كاش ولا حاجة لإعادة تشغيل) |
| المدير → موظف 1 بعد التعديل | موظف 1 يرى التسمية الجديدة |
| إعادة القيمة السابقة كمسؤول | `200` |
| عرض المكالمة نفسها بعد الإرجاع | تظهر التسمية المُرجَعة (التسمية تُقرأ وقت العرض) |

### المجلد 9 — رقابة المسؤول (بيانات وصفية فقط)

| الخطوة | المتوقع |
| --- | --- |
| `GET /api/calls/oversight` كموظف عادي | `403` |
| `GET /api/calls/oversight` كمسؤول النظام | `200` ومصفوفة `calls` |
| محتوى كل عنصر | `id`, `status`, `callType`, التواريخ، `durationSeconds`, `endedReason`, `metadata` فقط |
| كل مكالمة في القائمة | تشمل المدير أو الوكيل (`callerOrgUnitKind` أو `calleeOrgUnitKind` بقيمة `root` أو `deputy`) |
| عدم وجود بيانات هوية | لا `caller` ولا `callee` ولا `callerEmployeeId` ولا `calleeEmployeeId` |

> دور `auditor` يستطيع قراءة هذا المسار أيضاً. لا يمنح هذا المسار أي صلاحية
> لعرض المكالمة غير المخفية؛ عرض المشارك يبقى عبر `GET /api/calls/:id` فقط.

## 5. التحقق من سجل التدقيق (اختياري)

```sql
SELECT id, action, metadata, created_at
FROM audit_log
WHERE action = 'call.denied'
ORDER BY id DESC
LIMIT 10;
```

يجب أن ترى محاولات الموظف نحو المدير والوكيل والهدف غير الموجود والنفس، مع اختلاف
`metadata.reason` فقط، بينما الاستجابة العامة متطابقة.

## 6. حل المشاكل الشائعة

| المشكلة | السبب والحل |
| --- | --- |
| `401` | انتهت صلاحية رمز الوصول (`ACCESS_TOKEN_TTL`). أعد تشغيل مجلد تسجيل الدخول. |
| `429 CALL_RATE_LIMITED` | حد الدعوات لكل مستخدم (افتراضياً 10 في الدقيقة). انتظر دقيقة، أو ارفع `CALL_INVITE_RATE_MAX` في `backend/.env` وأعد تشغيل الخادم. |
| لا يجد الحسابات التجريبية | شغّل `npm run seed:calls --prefix backend` ثم أعد البحث. |
| `403` في تعديل الإعدادات بحساب المدير | تأكد أنك تستخدم `adminAccessToken` الخاص بـ `dev.admin`. |
| المتغيّرات فارغة | تأكد من اختيار البيئة الصحيحة في Postman قبل التشغيل. |
| فشل `seed:calls` بسبب وحدة تنظيمية | شغّل الترحيلات أولاً: `npm run migrate --prefix backend`. |

## 7. ملاحظات

- سكربت البذور `backend/scripts/seed-call-demo-users.js` لا يعمل إذا كان `NODE_ENV=production`.
- لا يستخدم أي كود مكالمات جدول `employee_contacts`؛ يبقى قائمة مفضّلة فقط.
- لا توجد قواعد نطاق شجرية ولا رؤساء وحدات ولا استثناءات إدارية في التفويض.
- القيادة تُحدَّد فقط بنوع الوحدة `root` أو `deputy`.
